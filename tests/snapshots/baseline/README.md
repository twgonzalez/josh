# Baseline regression snapshots

Captured: 2026-05-17 (Stage 0, Step 1 per `docs/plan-multihazard-stage-0.md` §6.3).

These are the production-Berkeley outputs as they exist BEFORE any multi-hazard work
landed in production code paths. Every later Stage 0 step must preserve byte-identical
output when `multihazard: false` (the default). Any drift from these snapshots while the
flag is off is a regression to fix, not a snapshot to update.

## What's NOT captured

- **`sidebar_state.json`** — listed in `plan-multihazard-mvp.md` §13.1 as a desired
  snapshot. Producing it requires running `analysis_map.html` in a headless browser
  to inspect post-hydration sidebar state. Deferred — `josh_data.json` carries the
  upstream truth (the sidebar derives from it), so byte-identical `josh_data.json` +
  unchanged `sidebar.js` source implies byte-identical sidebar state. We can add a
  headless-browser capture later if a regression surfaces that this would have caught.
- **`graph.json`, `parameters.json`, `fhsz.json`** — also exist in `output/berkeley/`,
  but are subsets of what's already in `josh_data.json`. Not duplicated here.

## How later steps consume this

- Step 2 (flag plumbing) — flag-off output must match `josh_data.json` byte-for-byte.
- Step 4 (emit `hazard_polygons.wildfire`) — flag-on output adds keys but doesn't
  modify existing v1 keys. `josh_data.json`'s top-level keys remain identical when
  flag off.
- Steps 21–22 (brief renderer v1/v2 branching) — v1 path must produce briefs byte-identical
  to `briefs/*.html`.
- Step 28 (Stage 0 PR review) — final full diff against this directory; any drift on
  flag-off path is a fail.

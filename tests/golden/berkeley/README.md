# Berkeley Wildfire Golden Files

Hand-verified expected outputs for the Stage 1 hazard engine (Berkeley, wildfire only).

Per `docs/plan-multihazard-stage-1-hooks.md` §10, these files are the **legal
artifact of record** for the methodology — the engine's output must match these
files field-by-field. Updates require explicit reviewer sign-off.

## Source of truth

Values derived from:
- **`output/berkeley/test_vectors.json`** — raw per-path ΔT outputs generated by `WildlandScenario.evaluate()` from `build.py map`
- **`static/multihazard_fixtures.js`** — the rolled-up controlling-result-per-hazard shape that the JS sidebar consumes today

Both files agree on the wildfire numbers for these 6 projects (same Python pipeline run, two serialization formats). The golden files are the canonical projection.

## What's NOT validated by these files

- `route_coords` — per-hazard route geometry computed at runtime; deliberately
  omitted from `expected` so minor edge-geometry changes don't fail the test.
  Validate via the Playwright smoke tests instead.
- Flood / tsunami / dam / gas / landslide hazards — these golden files are
  wildfire-only because Stage 1 ships only the wildfire adapter. Other-hazard
  golden files land when those adapters ship (Stages 3, 6, 7, 8, 9).

## Update protocol

Updating an expected output requires:
1. Documented methodology change (parameters.yaml diff, locked-decision update, or PR description naming the legal/methodology rationale)
2. Reviewer sign-off in the PR (not the engineer who wrote the change)
3. Updated `_provenance.computed_date` and `_provenance.methodology` fields
4. Diff against the previous expected file in the PR description

If the engine output diverges from the golden file and the divergence was
**unintentional**, the engine has a bug — fix the engine, do not update the
golden file.
